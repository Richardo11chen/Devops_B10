# AI使用记录

工具/模型/日期：
AI 编程助手（WorkBuddy，底层模型 DeepSeek-V4.1-Flash），2026-11-03。

输入上下文与问题：
向助手提供 E8–E10 材料包、`labs/e8e10/lab.py` 与 `test_profile.py` 源码、E8/E9 的实际运行日志。问题有两次：
（一）现有 7 项测试里哪些行为没被覆盖，选一个能守住「只修 MD、不动 RD」边界的新用例；
（二）E9 的自主任务选「重复依赖去重」，先判断当前实现是否真有这个问题。

模型建议：
- 第一次：指出 `test_patch_preserves_redundant_dependency` 只覆盖「有 MD 时顺带保留 RD」，没有覆盖「报告只有 RD、无 MD」这个输入类别；建议断言空 diff、空 plan、字节不变、`unused.h` 仍在。
- 第一次附带建议做变异测试验证用例有效性。
- 第二次：读完 `patch()` 后判断「重复追加」很可能存在（循环内每次都对目标行重新追加，没有去重），建议先写测试观察再改。

采纳/拒绝及理由：
- 采纳「只有 RD 的报告不应产生任何动作」的用例方向（E8）。
- 采纳变异测试做法；**但第一次提的变异（顺手删 RD）被否**：助手自己跑完发现旧测试也能捕获，不构成新测试的独占价值，于是追加第二种变异（无 MISSING 时静默重写文件）才证明独占覆盖。
- 采纳「先写测试确认 bug 再修」的顺序（E9），理由是避免改完才发现问题不存在。
- 拒绝「在 scan() 出口对 findings 去重」的方案：手写报告会绕过该处，守卫应放在 `patch()`。

人工修改：
- 选定两个自主任务的方向（E8 选项 1、E9 重复依赖去重）；
- 确认断言集合与独立预期的写法（先写预期、后跑代码）；
- 复核 `patch()` 的 `STALE_REPORT` / `UNSUPPORTED_*` 分支存在，确认新用例不与既有分支冲突；
- 修正助手第一版测试的落点：把断言从「diff 里不含 config.h」改为「plan 长度为 1」，因为前者在重复追加时仍然成立（`config.h config.h` 仍含 config.h）。

实际验证命令/输入/结果：
- `python3 -m unittest discover -s labs/e8e10 -p test_profile.py -v` → `Ran 9 tests ... OK`，退出 0。
- 变异 1（删 RD）：新旧测试均失败 → 无独占价值。
- 变异 2（无 MISSING 时去掉末尾换行）：仅新测试失败 → 独占覆盖成立。
- 变异 3（删除幂等守卫）：`test_duplicate_missing_entries_added_once` 失败（`2 != 1`）。
- 修复后重跑 E9：三份 patch 与修复前逐字节一致。

边界说明：
`lab.py` 的算法逻辑中，AI 只提议了 `patch()` 内一段去重守卫（6 行），是否采纳与最终写法经人工确认；其余实现未改。所有结论以实际运行日志为准。
