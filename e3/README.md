# E3 — 并行测试基线（B10）

准备能让工具接受的测试项目，写出预期结果和判断依据，保留实际运行或失败记录。

**A 组负责**：MD/RD 故障项目、C0/C1/C2 连续提交、Linux 原始跟踪（strace、`make -pn`）。
**B 组负责**：DRAFT 样本、MDFixer 固定输入。

## 基线必须包含的四要素

任何一条基线记录都必须同时写清：

1. **固定项目版本和环境** — commit SHA、工具版本、运行平台
2. **本次修改或故障是什么** — 改了什么 / 坏在哪
3. **预期输出及判断依据** — 应该看到什么，为什么是这个
4. **可重新执行命令** — 别人照着敲就能复现

## 目录约定

| 目录 | 放什么 | 可否算作"真实证据" |
|------|--------|-------------------|
| `fixtures/` | **课程人工样例源码**（人工构造，非真实 Git 历史） | 否，必须标 `ORACLE` 来源 |
| `work/`（仓库根） | **真实 Git 提交与参考修复** | 是 |
| `evidence/` | **实际命令和观察结果**（原始日志、退出码、镜像 ID） | 是 |

**每次运行新建一个目录，保留旧证据，不要覆盖。** 人工构造的预期结果必须显式标注 `ORACLE`，与真实运行日志区分开。

> 待确认：`evidence/` 是否也采用 `<YYYYMMDD-HHMMSS>/` 时间戳子目录（参考 A 组 `e3/work/` 的做法）。组长确认后更新本节。

## B 组两块任务概览

### 1. DRAFT 样本（成员C）

两层成功判据，**缺一不可**：

| 层次 | 判据 | 要保存 |
|------|------|--------|
| 第一层 编译通过 | 构建命令退出码 0，预期可执行文件生成 | 构建日志 |
| 第二层 功能验证 | 运行 README 约定测试，检查退出码与预期输出 | 测试输出（**失败也要记录**） |

必须交付的三个候选：

- **`Dockerfile.broken`（失败候选）** — 基于 `python:3.13-slim`，直接 `RUN make`，预期非零退出，日志出现 `make: not found`
- **`Dockerfile.reference`（参考成功）** — 安装 `gcc make libc6-dev`，预期构建成功，容器内输出 `hello E3`
- 要保存：Dockerfile diff、build 退出码、日志、镜像 ID

### 2. MDFixer 固定输入（成员D）

固定输入四件套：

- 固定 MD 报告（`main.o` 缺 `config.h`）
- 同一源码版本的 Makefile
- 构建命令与行为测试
- 预期声明风格

四种声明风格：**Target、Macro、Hybrid、Implicit**。参考 Patch 至少给出 **Target** 风格，并说明其他风格差异。

隐式规则与 `.d` 文件：`%: %.c` 使用 `$(CC) -MMD -MP -c $< -o $@`，`-include main.d`；需检查 `.d` 内容和再次修改头文件的行为。
